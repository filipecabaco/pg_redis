PostgreSQL extension · Rust + pgrx · PG 15–18

Redis, spoken by Postgres.

pg_redis runs a Redis server inside PostgreSQL. Point any Redis client at port 6379, and choose per database where the data lives: shared memory, memory with snapshots, or tables you can query, join and back up. Change it while clients keep writing.

Storage, chosen per database

Each of the 16 databases has its own policy. By default 0–7 are ephemeral and 8–15 durable, and SELECT cache and SELECT durable still pick one of each. Any of them can change at runtime.

Moves while you use it

Changing a policy between memory and tables moves the data online. Each key moves the moment a command touches it, and a background sweep moves the rest. Clients keep reading and writing throughout, and no key is lost on the way. Between memory and memory+snapshot nothing moves at all.

How migration works 
-- every database, its policy, and any move in progress
SELECT * FROM redis.policies();

-- make db 3 durable; its keys follow
SELECT redis.set_policy(3, 'logged');

-- keep db 0 in memory, but snapshot it
SELECT redis.set_policy(0, 'memory+snapshot');

Memory, the way Redis does it

The memory engine grows with your data up to redis.maxmemory, 256 MB by default. The space is reserved at startup, but it only takes RAM as keys fill it.

  • Keys and values up to 512 MB, as in Redis, and all 16 databases can be in memory at once.
  • Past the limit, a write gets OOM, or keys are evicted per maxmemory-policy: noeviction, allkeys-random or volatile-ttl.
  • Every memory command runs under one lock, so each is fully atomic. Sorted sets keep an ordered index, so ZRANGE, ZRANK and ZPOPMIN don't scan.
  • Written in safe Rust. The only unsafe code is one small module, and running out of memory returns OOM instead of crashing.

More than GET and SET

Every core type

Strings, hashes, lists, sets and sorted sets, written once for memory and tables, so every policy gives the same replies and errors.

Streams

XADD, consumer groups, XREADGROUP, XAUTOCLAIM.

Pub/Sub

Channels, patterns and RESP3 push frames, fanned out across every worker.

Lua & Functions

EVAL, EVALSHA, FUNCTION LOAD, running on an embedded Lua 5.1.

Transactions

MULTI/EXEC and optimistic WATCH, plus the blocking commands: BLPOP, BZPOPMIN, XREAD BLOCK.

The long tail

HyperLogLog, GEO, client-side caching with CLIENT TRACKING, OBJECT, SCAN, SLOWLOG.

At parity with Redis on Redis's own Tcl acceptance suite and on a reply-by-reply diff against Redis 7.2, both run in CI, apart from a few minor deviations listed below. See every command

Install

The extension listens on its own port, so it has to be preloaded. Add it to shared_preload_libraries, restart, and create it.

Installation guide 
# build and install into the active Postgres
cargo pgrx install --release --features pg17

# postgresql.conf
shared_preload_libraries = 'pg_redis'

# after a restart
psql -c 'CREATE EXTENSION pg_redis'
redis-cli PING   # PONG

Good to know

  • The Redis port does not go through pg_hba.conf. It binds to 127.0.0.1 by default; set a password before widening it.
  • Memory databases share one arena of redis.maxmemory, reserved at server start. Raising it needs a restart; CONFIG SET maxmemory can only lower it.
  • A command's first touch of a key that hasn't moved yet pays for the move, and a command that needs the whole database (KEYS, SCAN, FLUSHDB) finishes the migration first.
  • It needs shared_preload_libraries and a superuser, so it runs where you control the server, not on managed Postgres that doesn't offer it.

Where it differs from Redis

pg_redis passes the same tests as Redis: Redis's own Tcl acceptance suite, and a diff of every reply against Redis 7.2. These are the deviations that remain. Full detail

Behaviour

  • Atomicity is per worker. Each command is atomic, but the commands inside a script or MULTI can interleave with other workers' commands. Redis runs on one thread, so nothing interleaves.
  • Blocked clients are served just after the write. A write that unblocks BLPOP clients waits up to 500 ms for them to be served, where Redis serves them inside the write.
  • Small hashes and sets keep insertion order only until a removal. Redis documents both as unordered, but a client can see the difference.
  • No access clock. OBJECT IDLETIME and OBJECT FREQ return nil, since tracking reads would turn every read on a table into a write.
  • A stand-alone server, with one user. REPLICAOF, WAIT, CLUSTER and ACL answer as Redis would with no replicas, no cluster and only the default user. Replication is PostgreSQL's.
  • GEO distances can differ in the last digit of a stored float. It is the only difference the reply diff still finds.
