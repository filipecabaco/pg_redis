PostgreSQL extension · Rust + pgrx · PG 15–18

Redis, spoken by Postgres.

pg_redis runs a Redis server inside PostgreSQL. Point any Redis client at port 6379, and choose per database where the data lives: shared memory, memory with snapshots, or WAL-logged tables you can query and join. Change it while clients keep writing.

Storage, chosen per database

Each of the 16 databases has its own policy. By default 0–7 are ephemeral and 8–15 durable, and SELECT cache and SELECT durable still pick one of each. Any database's policy can change at runtime.

Moves while you use it

Changing a policy between memory and tables moves the data online. Each key moves the moment a command touches it, and a background sweep moves the rest. Clients keep reading and writing throughout, and no key is lost on the way. Switching between memory and memory+snapshot moves no data.

How migration works 
-- every database, its policy, and any move in progress
SELECT * FROM redis.policies();

-- make db 3 durable; its keys follow
SELECT redis.set_policy(3, 'logged');

-- keep db 0 in memory, but snapshot it
SELECT redis.set_policy(0, 'memory+snapshot');

Memory, the way Redis does it

The memory engine grows with your data up to redis.maxmemory, 256 MB by default. The space is reserved at startup, but it only takes RAM as keys fill it.

  • Keys and values up to 512 MB, as in Redis, and all 16 databases can be in memory at once.
  • Past the limit, a write gets OOM, or keys are evicted per maxmemory-policy, with all eight of Redis's policies: noeviction, allkeys-lru, allkeys-lfu, allkeys-random, volatile-lru, volatile-lfu, volatile-random and volatile-ttl. LRU and LFU use Redis's sampled approximation and its 24-bit access clock, so OBJECT IDLETIME and OBJECT FREQ answer as in Redis. An evicted key raises the evicted event and a CLIENT TRACKING invalidation.
  • A memory command holds its database's lock from start to finish, so a single command such as INCR is atomic. Scripts, MULTI and commands built from others, such as ZUNIONSTORE, hold the database for their whole run on every worker, as in Redis, while other databases keep running. Sorted sets keep an ordered index, so ZRANGE, ZRANK and ZPOPMIN don't scan.
  • The memory engine's unsafe code is confined to one small module, shm.rs. Running out of memory returns OOM instead of crashing.

Throughput

Requests per second, higher is better: 230k/s is 230,000 commands answered every second. redis-benchmark, 50 clients, 64-byte values over 100,000 random keys, median of 5 runs. Each server pinned to the same 4 CPUs, Docker on Apple Silicon. Each client sends one command at a time, with no pipelining. memory+snapshot runs within 2% of memory. logged writes commit to PostgreSQL's write-ahead log and wait for it to reach disk, so the disk sets their rate; reads stay fast. More than GET and SET

Every core type

Strings, hashes, lists, sets and sorted sets, written once for memory and tables, so every policy gives the same replies and errors.

Streams

XADD, consumer groups, XREADGROUP, XAUTOCLAIM.

Pub/Sub

Channels, patterns and RESP3 push frames, fanned out across every worker.

Lua & Functions

EVAL, EVALSHA, FUNCTION LOAD, running on an embedded Lua 5.1.

Transactions

MULTI/EXEC and optimistic WATCH, plus the blocking commands: BLPOP, BZPOPMIN, XREAD BLOCK.

The long tail

HyperLogLog, GEO, client-side caching with CLIENT TRACKING, OBJECT, SCAN, SLOWLOG.

Install

The extension listens on its own port, so it has to be preloaded. Add it to shared_preload_libraries, restart, and create it.

Installation guide 
# build and install into the active Postgres
git clone https://github.com/filipecabaco/pg_redis && cd pg_redis
cargo pgrx install --release --features pg17

# postgresql.conf
shared_preload_libraries = 'pg_redis'

# after a restart
psql -c 'CREATE EXTENSION pg_redis'
redis-cli PING   # PONG

Good to know

  • The Redis port does not go through pg_hba.conf. It binds to 127.0.0.1 by default; set a password before widening it.
  • Memory databases share one arena of redis.maxmemory, reserved at server start. Raising it needs a restart; CONFIG SET maxmemory can only lower it.
  • A command's first touch of a key that hasn't moved yet pays for the move, and a command that needs the whole database (KEYS, SCAN, FLUSHDB) finishes the migration first.
  • pg_dump and physical backups both include the logged databases, the snapshots of memory+snapshot ones and the policies. memory databases are in no backup, as in Redis without persistence.
  • It needs shared_preload_libraries and a superuser, so it runs on servers you control, and on managed Postgres only where the provider offers both.

Where it differs from Redis

Measured against Redis's own Tcl acceptance suite and a diff of every reply against Redis 7.2. These are the deviations that remain. Full detail

Behaviour

  • SCAN cursors on tables are kept by the server. On a logged database a cursor names the last key returned, and the server keeps up to 4,096 iterations in progress. The cursor from the latest call, or from the one before it, resumes where it left off, which covers a client retrying a lost reply. An older cursor, or one pushed out by newer iterations, starts the iteration over, so keys come back again. None is skipped.
  • Blocked clients are served just after the write. A write that unblocks BLPOP clients waits up to 500 ms for them to be served, where Redis serves them inside the write.
  • Logged keys' access times are kept in a fixed table. OBJECT IDLETIME and OBJECT FREQ answer for a logged database from a 65,536-slot table in shared memory, so a read never writes a row. Two keys that share a slot share a clock, and the table starts empty after a restart.
  • Memory data does not fail over. On a promoted standby, memory databases start empty, as a Redis primary without replicas would. A memory+snapshot database is snapshotted at shutdown, so a planned switchover keeps every write; after an unplanned one it loads its last snapshot.
  • A stand-alone server, without modules. Redis replication, cluster mode and modules are out of scope: REPLICAOF, WAIT and CLUSTER answer as Redis would with no replicas and no cluster, and MODULE answers that no modules are loaded. Replication is PostgreSQL's.
  • ACL users are saved to a table. Users, their rules and the checks follow Redis 7.2. ACL SAVE and ACL LOAD write and read redis.acl_users where Redis uses an ACL file; ACL SETUSER alone does not survive a restart, as in Redis.
  • Floats follow Redis on x86-64. INCRBYFLOAT and HINCRBYFLOAT add in 80-bit long double and print the digits Redis prints on x86-64. Redis builds on arm64 use a 128-bit long double and round GEO distances differently, so against them these can differ in the last digit. These are the only differences the reply-by-reply diff finds, and only against arm64 Redis.
